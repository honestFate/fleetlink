# Решения по проекту

Список заметок и решений по проекту

## Алгоритм доступа

Выбран Ricart–Agrawala для вместимости 1 и его обобщение k-exclusion
для вместимости k, с повторами сообщений, дедупликацией и локальным
исключением молчащих участников по тайм-ауту HEARTBEAT

- LOADING_BUFFER и UNLOADING_BUFFER - буферы погрузки и разгрузки вместимостью k
  Обслуживание происходит внутри, ресурсы оборудования - LOADING_SERVICE и UNLOADING_SERVICE
- Работать со станцией загрузки и отгрузки решено считать что может одновременно
  только одна машина
- Для ресурса вместимостью c нужны ответы `max(0, |active_i| - c)` разных
  участников, где `active_i` - локальный состав, включая саму машину
- Свободная машина отвечает сразу, ожидающая откладывает ответ запросу
  с более поздним приоритетом, владелец - до освобождения ресурса
- Захват идёт в порядке буфер -> оборудование, освобождение - в обратном порядке
  Другой буфер запрашивается при приближении к нему
- тайм-аут не меняет физическую занятость в проверке И1
- АРМ не выдаёт разрешений, машины согласуют доступ только сообщениями

Выбор даёт общий порядок запросов без координатора и сложного восстановления
токена, а исключение по тайм-ауту позволяет пережить настоящий отказ в S3

HALT сразу останавливает движение и обслуживание, но сохраняет занятость
и обработку сообщений, включая HEARTBEAT
**И1 гарантируется только при отсутствии ложного исключения живых машин**
Например, остановленный в буфере владелец при долгой потере связи может быть
исключён, после чего другая машина войдёт сверх вместимости
Большой тайм-аут уменьшает риск, но не доказывает безопасность при любых потерях
Продолжение работы гарантируется при условии, что необходимые повторные сообщения
в итоге доставляются, обслуживание завершается, а HALT снимается и позволяет машине
освободить ресурс
Реальный отказ по принятой модели физически убирает машину с маршрута

Альтернативы: ожидание всех ответов без тайм-аута сохраняет безопасность,
но блокирует S3; аренда места не обеспечивает его освобождение при HALT;
токен требует безопасного восстановления после потери; кворумные слоты требуют
дополнительного разрешения конфликтов голосов и защиты от голодания

## Стек

Выбраны C++17 и STL, CMake ≥ 3.20, pybind11 для Python-модуля,
doctest и CTest для тестов, nlohmann/json для журнала в формате JSONL

Выбрал наиболее простые для себя варианты.
Основу взял из каркаса ТЗ, готовые библиотеки позволяют не писать собственные
средства тестирования, сериализацию JSON и привязку к Python
Главные критерии - простое подключение и сборка на чистой Linux-машине

Модель работает в одном потоке: для 4–10 машин этого достаточно,
так проще обеспечить воспроизводимость и избежать лишней синхронизации
Журнал и вывод телеметрии обрабатывает отдельный поток, как требует ТЗ
Машины обмениваются C++-структурами, JSON нужен только для вывода событий

Рассматривались C++20/23, Catch2/GoogleTest, прямой Python C API,
собственный JSON writer и journald, но для текущей задачи выбранного стека достаточно

В `third_party` включены doctest 2.4.12, nlohmann/json 3.12.0 и pybind11 3.0.1
Версии, источники и лицензии перечислены в `third_party/VERSIONS.txt`
Сборка не скачивает зависимости, нужны компилятор C++17, CMake ≥ 3.20 и make
demo.py оставлен на потом

Для стиля и статического анализа выбраны clang-format и clang-tidy 18.1.8
Стиль LLVM с отступом 4 пробела и длиной строки 100 символов
Команды CMake: `format`, `format-check`, `tidy`, проверяется только наш код
Инструменты устанавливаются из `requirements-dev.txt`, обычная сборка их не требует

## Детерминированное правило И3

Приоритет запроса - лексикографическая пара `(Lamport timestamp, machine id)`
Меньшая пара обслуживается раньше, при равных часах побеждает меньший id
Метка фиксируется при создании запроса и сохраняется при повторах
При получении сообщения часы обновляются как `max(local, received) + 1`

Id задаётся конфигурацией и сохраняется при перестановке машин, он не является
индексом в контейнере или номером, назначенным по порядку запуска
Для И3 также нужны одинаковые фазы тика, порядок обработки событий и назначение
случайных потерь/задержек независимо от порядка обхода контейнера
Проверка - сравнение прогонов с теми же id и seed при перестановке списка машин

Альтернативы: один id создаёт постоянный приоритет и риск голодания;
порядок поступления отличается у получателей; индекс и порядок запуска нарушают
И3; случайная ничья требует дополнительного согласования результата
Пара `(tick запроса, id)` возможна при явно общей шкале времени, часы Лэмпорта
выбраны для локального протокола с причинным порядком сообщений

## Сообщения и порядок тика

- Сообщения — C++-структуры через std::variant, доставка адресная или broadcast
- Реализован внутрипроцессный канал без дефектов, время продвигает World
  Канал хранит копии сообщений, чтение забирает накопленную очередь получателя
- Повтор REQUEST сохраняет номер попытки и приоритет, номер отправки обновляется
- Тик: доставка → обработка входящих и обновление машин → отправка накопленных исходящих
  Тик доставки — `sent_tick + max(1, delay)`, включая нулевую задержку
- Сообщения одного тика доставки и исходящие сортируются по `(sent_tick, sender, sequence)`,
  получатели — по id, чтобы результат не зависел от порядка обхода машин
- MISSION задаёт первую точку и запускает цикл погрузка → разгрузка без участия АРМ
  Новое задание применяется после текущего обслуживания и выхода из буфера
