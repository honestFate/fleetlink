# Решения по проекту

## Выбор решения

Приняты два буфера перед погрузкой и разгрузкой вместимостью k
Обслуживание идёт внутри буфера, по одной машине на станции
MISSION задаёт первую точку и запускает повторяющийся цикл погрузка - разгрузка

Выбран Ricart–Agrawala для одного места и его обобщение k-exclusion для k мест
Для ресурса вместимостью c нужны ответы `max(0, N - c)` разных участников,
где N - число машин, которые участник считает активными, включая себя
Свободная машина отвечает сразу, ожидающая уступает более раннему запросу,
получившая разрешение откладывает ответ до освобождения
Дубли и ответы на старые попытки не дают дополнительных разрешений

Приоритет - меньшая пара `(Lamport timestamp, устойчивый id)`
Метка сохраняется при повторах; id не зависит от индекса и порядка запуска
Один id дал бы постоянный приоритет, порядок прихода различается у получателей,
случайная ничья требует согласования
Пара `(tick, id)` возможна при общей шкале времени; часы Лэмпорта позволяют
опираться на локальные события и сообщения

Захват идёт в порядке буфер - оборудование, освобождение - в обратном порядке
RELEASE отправляется после фактического освобождения, другой буфер запрашивается
после выхода из исходного и прибытия к следующему
При k=1 отдельное согласование оборудования не нужно
Так нет циклического ожидания между ресурсами

REQUEST повторяется каждые 50 тиков, HEARTBEAT отправляется каждые 5
После более чем 200 тиков без нового HEARTBEAT участник локально исключается
из ожидания ответов; физическая занятость от тайм-аута не меняется
Настоящий отказ по принятой модели убирает машину с маршрута
HALT при получении замораживает движение и обслуживание, сохраняет загрузку
и занятые ресурсы, но обработка сообщений, включая HEARTBEAT, продолжается
Запросы на ещё не занятые ресурсы отменяются через CANCEL
Каждый инициатор снимает только свой HALT; для MISSION и HALT/RESUME есть ACK и повторы

Выбор даёт общий порядок без координатора и восстановления токена,
тайм-аут позволяет продолжать работу в S3
Без исключения молчащих ожидание безопаснее, но блокирует S3 при k=1
Аренда не освобождает физическое место при HALT; токен требует восстановления
после потери; кворумные слоты усложняют разрешение конфликтов и защиту от голодания

## Реализация и стек

Выбраны C++17/STL, CMake ≥ 3.20, doctest/CTest, nlohmann/json и pybind11
Это наиболее простые для меня варианты; до задачи опыт C++ ограничивался учебными проектами
doctest подключается одним заголовком, nlohmann/json заменяет ручную сериализацию,
pybind11 избавляет от ручного управления объектами через Python C API
Рассматривались C++20/23, Catch2/GoogleTest, собственный JSON writer и journald
Для текущей задачи выбранного стека достаточно
Зависимости включены в third_party с лицензиями, загрузок при сборке нет
Python-фасад и demo.py реализованы, нужны Python и dev-заголовки
Для стиля и статических проверок используются clang-format/clang-tidy 18.1.8

Для 4–10 машин выбран один поток модели: проще владение данными и воспроизводимость
Отдельный поток-потребитель форматирует и пишет JSONL, включая принятую телеметрию
Очередь защищена mutex, файловый вывод выполняется вне него; при закрытии очередь
дописывается, ошибки вывода передаются вызывающему коду

Транспорт - внутрипроцессные очереди C++-структур с unicast и broadcast
UDP и отдельные процессы усложнили бы сборку без пользы для проверки протокола
Машины получают чужое состояние только из сообщений, АРМ разрешений не выдаёт
Тик: доставка - обработка входящих и обновление машин - отправка исходящих
Доставка не раньше следующего тика, sleep не используется
Все сообщения, включая служебные, проходят через дефекты канала
Порядок событий фиксирован; потери, задержки и дубли зависят от seed и идентификаторов
отправки/получателя, не от порядка обхода машин
Для разбора сообщений нужен TRACE, по умолчанию demo.py пишет INFO

## Инварианты и проверки

- **И1**: порог разных ответов ограничивает число разрешений, владелец удерживает ресурс
  до освобождения; гарантия требует отсутствия ложных исключений
  World проверяет физическую занятость после каждого обновления, но разрешений не выдаёт
  test_world.cpp и test_capacity.cpp проверяют занятость по событиям, k=1, 2, 3, 6, 9,
  HALT, отказ в буфере и очередь на медленной разгрузке
- **И2**: постоянный приоритет и отложенные ответы дают продвижение при доставке повторов,
  отсутствии ложных исключений, конечном обслуживании и конечном HALT
  Для S2 на seed 0, 1, 7, 42, 12345 в test_world.cpp проверяется ожидание менее
  1500 тиков, включая незавершённые ожидания
  При seed=42 максимум завершённого ожидания S2 - 369 тиков, S5 - 452
  Это результаты конечных прогонов; без ограничения серий потерь общей границы нет
- **И3**: перестановки состава и порядка обработки сохраняют состояния и журналы
  при тех же id, seed и параметрах - test_protocol.cpp, test_world.cpp,
  test_capacity.cpp и test_python.py
  Изменение самих id может изменить исход ничьей
- **И4**: через 201 тик без нового HEARTBEAT ожидание молчащего участника прекращается
  В S3 M3 отказывает на тике 1000 после REQUEST и до входа
  test_world.cpp проверяет peer_excluded у остальных и продолжение их работы
- **И5**: после запуска цикла АРМ не нужен для согласования
  Тест S4 сравнивает движение с доступным и отключённым АРМ на тиках 800–1000,
  затем проверяет восстановление телеметрии; старые сообщения не обновляют её давность

Прошли 109 C++-тестов, 9 Python-тестов, все 12 проверок CTest
ASan проверен на C++-тестах, TSan - на S1/S2 с журналом и без него и тестах flush
Два прогона S5 дали одинаковые отчёты и журналы INFO; S5 под TSan не подтверждён
[Выводы тестов](validation/tests.txt), сценариев и санитайзеров сохранены в validation
Сборка проверена из свежей копии Git в Ubuntu в WSL, не на чистой ОС

## Ограничения и следующий шаг

Тайм-аут не отличает отказ от потери связи
Если живой владелец остался в буфере, например после HALT, но исключён из-за потерь
HEARTBEAT, другая машина может войти сверх k
В test_machine.cpp тест `known limitation: falsely excluding a live holder can exceed physical capacity`
воспроизводит нарушение И1
При разделении сети безопасность не гарантирована, больший тайм-аут лишь уменьшает риск
Бесконечная потеря нужных сообщений или неснятый HALT нарушают прогресс
HALT погибшего инициатора автоматически не снимается, что также ограничивает И4

Сознательно не моделируются столкновения и дистанция: машины могут ждать на одной
координате вне буфера, отказ освобождает место
Это проверка согласования ресурсов, а не безопасности движения
Состав фиксирован, перезапуска погибшей машины нет
Временное отключение узла реализовано и проверено в транспорте, но в World/Python
доступно только для АРМ; сценария OFFLINE и возврата машины нет
S3 при других seed/k может не застать M3 в ожидании на тике 1000 и явно завершится ошибкой
Очереди не ограничены, поэтому медленный вывод увеличивает расход памяти
Адаптивный детектор отказов и восстановление после разделения сети не реализованы

Для S5 (10 машин, 100 000 тиков) подробный TRACE создаёт большой объём записей,
а TSan добавляет накладные расходы по памяти и времени
Пробный нативный S5 с TRACE под TSan был остановлен вручную после превышения
7 ГБ RSS - это незавершённый прогон, он не подтверждает чистоту под TSan
Подтверждённые повторные прогоны S5 используют INFO и файловый журнал;
demo.py считает его SHA-256 по частям, не загружая файл целиком
Запись в файл не ограничивает очередь Logger: если потребитель отстаёт,
записи продолжают накапливаться в памяти
При работе через Python без log_path весь журнал хранится в памяти,
а вызов events() дополнительно создаёт коллекцию записей, поэтому такой способ
не подходит для чтения полного длинного TRACE

При наличии ещё дня добавил бы потерю покрытия и возврат машины через World/Python
с явным поведением OFFLINE и тестами короткого разрыва и разрыва дольше тайм-аута,
включая HALT в буфере, чтобы показать границу между отказом и потерей связи
